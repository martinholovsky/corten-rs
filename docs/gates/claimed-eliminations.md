# Plan: confirming the claimed eliminations

Date: 2026-10-27. Scope: the 33 CWEs that can be written in safe Rust, sit in bucket E, and are not `verified`. They are the hatched segment of [`docs/assets/cwe-rust-corten.svg`](../assets/cwe-rust-corten.svg) (generated by `scripts/applicability-chart.py`). The ledger has 34 unverified E rows in all; the 34th cannot be written in safe Rust, so it is not on the chart.

What confirms a row does not change (AGENTS.md rule 1): its corpus case, **every bypass variant included**, fails to build under `cargo corten check`, the matched good program builds, the false-rejection rate is reported beside it, and `corten-corpus --mark-verified` sets `verified`. Rows with `review = required` also need the independent review recorded first. A row confirmed this way moves from the hatched segment to the dashed one. A row that cannot be confirmed leaves bucket E, with its reason in the ledger, and joins the solid part of the bar: it is then counted as writable under Corten, as it should have been.

Groups were counted from `ledger/cwe-ledger.csv` and `docs/gates/corpus-report.md` on 2026-10-27.

## A. Detected; waiting for the encoder review (25)

CWE-77, 78, 79, 80, 81, 82, 83, 84, 85, 86, 87, 89, 90, 91, 93, 113, 117, 643, 644, 652, 692, 838, 943, 1236, 1336.

The corpus already rejects every bad program (`pass (awaiting encoder review)`). The claim rests on `corten-std`'s encoders, which their author cannot review ([`phase-2.md`](phase-2.md) section 5 lists what the reviewer must check).

1. Name a reviewer who did not write the encoders. **Owner decision.**
2. Give them a review packet: for each encoder file, the rows resting on it and the section 5 checklist.
3. Add evidence that makes the review cheaper, not a substitute for it:
   - property tests (escaped `Html` re-parsed adds no element or attribute; `sql!` placeholders never fall inside a quoted literal);
   - a differential test against an independent parser, if one passes `cargo deny`.
4. The reviewer replaces `required` with a link to the review, then `--mark-verified`.

Falsified if the review or a property test finds an escape that lets an injected value change the structure of the output. That row then needs a fix and a corpus variant before it can be verified.

## B. Name-based ban list; a renamed engine passes (4)

CWE-611, 776, 827, 1333. Each has a `bad-unlisted.rs`: the same backtracking regex or DTD-capable XML engine under a name the ban list does not know. It passes the checker (exit 0). A list of names cannot see what a crate does, so no amount of extra testing confirms these rows. Options:

1. **Reclassify to C**, with the ban list kept as a policy aid. This is the honest reading of what the mechanism does. *Recommended.*
2. Deny dependencies by default: only operator-allowlisted crates build. The unlisted engine is then refused like any other unlisted crate. This changes the dependency policy for every user, and its false-rejection rate has to be measured against the 5% threshold first.

**Owner decision** (security-relevant: it moves a trust boundary).

## C. Rules narrowed by an earlier decision (2)

- **CWE-252** (`bad-std-status.rs`): a status from a standard-library function is discarded. Owner decision 10 narrowed must-use to callees in the checked crate. To close it, extend `corten_must_use_return` to std functions that return a status (`bool`, `Option`, `Result`). Then measure false rejections on the corpus and on a sample of real crates, against the 5% threshold. If it fits, propose lifting the narrowing.
- **CWE-683** (`bad-private.rs`): a swap through a private function. The lint covers exported functions (spec 4.2). Covering every function falsely rejected 4 of 174 matched good programs ([`phase-3b.md`](phase-3b.md)), under the 5% threshold. Re-measure and propose extending it.

Both reverse earlier owner positions, so both are **owner decisions**. If either is declined, that row moves to C.

## D. A catch-all through `thread::join` (1)

**CWE-396** (`bad-thread.rs`): `JoinHandle::join` returns a child's panic as `Err`, which works as a catch-all handler. The phase 1 bypass hunt found it ([`phase-1.md`](phase-1.md)). Options:

1. Ban `JoinHandle::join` in application code and route spawning through `corten-runtime`'s supervisor, which already sees panics through the join result. Measure false rejections first. Phase 1 expected banning `join` outright to reject ordinary code.
2. Reclassify to C.

**Owner decision.**

## E. Not built (1)

**CWE-619** (dangling database cursor). The ledger names `corpus/CWE-619` as its proof, but that case does not exist. [`phase-2.md`](phase-2.md) records that the prelude has no database cursor API. Options:

1. Build an affine `Cursor` in `corten-std`, released only by its owner's drop. Add a corpus case: a bad program uses the cursor after release, and a good one does not.
2. Reclassify to C until a cursor API exists.
